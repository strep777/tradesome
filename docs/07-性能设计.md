# TradeSome 性能设计

> 一句话：**性能预算写死，超出即缺陷。** 桌面软件的性能问题 90% 来自"UI 线程干重活"和"每帧全量重绘"，本文件针对这两点设计。

---

## 1. 性能预算（硬指标）

| 场景 | 预算 | 测量点 |
|---|---|---|
| 冷启动 → 主窗口可见 | ≤ 3.0s | `__main__` 入口 → `Shell.run()` 返回 |
| 页面切换（已构造） | ≤ 100ms | 点击导航 → 新页 `on_show()` 完成 |
| 页面首次构造 | ≤ 400ms | 首次 `navigate` |
| 1 万根 bar 单标的回测 | ≤ 2.0s | `BacktestEngine.run()` |
| 50 万根 bar 落库 | ≤ 30s | `upsert_bars` |
| 单次 K 线重绘（250 根） | ≤ 50ms | `ChartCanvas.redraw()` |
| 事件总线单次发布（10 订阅者） | ≤ 1ms | 基准脚本 |
| 模拟盘 tick 间隔抖动 | ≤ 20% | 目标 1s/次 |
| 常驻内存（空载 + 1 万 bar） | ≤ 300MB | 任务管理器 |
| 数据库文件（8 标的 × 3 年日线） | ≤ 20MB | 文件大小 |

> 参考机：4 核 / 8GB / 集显 / Windows 11 / Python 3.9。低于此配置允许 50% 放宽。

## 2. 复杂度分析

| 模块 | 复杂度 | 说明 |
|---|---|---|
| `BacktestEngine.run` | O(B × S) | B=时间步数，S=标的数；每步只做 O(S) 的字典操作 |
| `MatchingEngine.match` | O(1)/单 | 只读当根 bar 与订单 |
| 指标（SMA/EMA/RSI/ATR…） | O(n) | 单遍扫描；预计算一次，按索引切片 |
| `Account.mark_to_market` | O(P) | P=持仓数（≤ 50） |
| `metrics.compute` | O(B) | 净值曲线单遍 |
| `BarRepository.get_bars` | O(log n + k) | 索引 `(symbol, dt)`；k=返回行数 |
| `upsert_bars` | O(k) | `executemany` 单事务 |
| `CandlestickChart.redraw` | O(V) | V=可见 bar 数（抽稀后 ≤ 250） |
| 事件总线发布 | O(S) | S=订阅者数；复制列表 |

**禁止的写法**：在 bar 循环里查数据库、在 bar 循环里 `str.format` 拼接大字符串、在 `on_bar` 里重算全量指标。

## 3. 关键设计

### 3.1 指标预计算与切片视图

策略 API `ctx.history(symbol, n)` 返回**切片拷贝**（长度 n），而不是全量列表：
- 引擎为每个标的维护 `close/high/low/volume` 的 `array('d')`；
- `history` 用 `arr[max(0,i-n+1):i+1]` 生成 list（n 通常 ≤ 250，拷贝成本可忽略）；
- 指标库为纯函数，策略可缓存（例如 `on_start` 建 `self._ma = None`，首次计算后按索引取）。

### 3.2 回测主循环热点优化

```python
# 冷路径：每根 bar 只做这些
for i, dt in enumerate(timeline):
    bars = {s: series[s][i] for s in active}      # dict 推导，S ≤ 10
    self._match_pending(bars)                     # 通常 0~2 单
    self.account.mark_to_market(bars, dt)         # P ≤ 50
    self.strategy.on_bars(ctx, bars)              # 用户代码
    if i % 50 == 0: progress(i, total)            # 节流
    if cancel.is_set(): break
```
- 预先把 `bars_by_symbol` 对齐到统一 timeline（缺失标的用 `None`，停牌日跳过）；
- 权益快照用 `list.append`，结束时一次性转 tuple；
- 进度回调节流：每 50 根或 ≥ 100ms 一次（取先到者）。

### 3.3 图表绘制：抽稀 + 增量

- **抽稀（LOD）**：可见 bar 数 > 260 时，按"每像素至少 1 根"合并为 OHLC 桶（开=首、收=末、高=max、低=min、量=sum），保证绘制量恒定；
- **分桶缓存**：`(symbol, timeframe, width, range)` → 预计算绘制点，窗口不变直接复用；
- **Canvas 复用**：重绘前 `delete("all")` 在 Tk 上是 O(1) 交给底层，但仍应避免每帧重建 > 2000 个 item；实测 250 根 K 线（约 1500 item）重绘 ~15ms；
- **去抖**：`<Configure>` 事件 80ms 去抖，避免拖拽窗口时狂重绘；
- **字体/颜色对象复用**：`theme.py` 里缓存 `tkfont.Font` 与颜色字符串，不在绘制循环里新建。

### 3.4 数据访问

- `BarRepository` 的 LRU：容量 8 个 `(symbol, timeframe)`，每项 ≤ 6000 根；
- 批量读取：`get_bars_many` 用一条 `IN (...)` 查询 + 内存分组，避免 N 次查询；
- 写入：单事务 `executemany`，每 5000 行提交一次（大文件导入）；
- 索引只建必要的：`(symbol, dt)`、`orders(client_id)`、`audit_log(ts)`；多余索引拖慢写入。

### 3.5 启动优化

| 阶段 | 措施 |
|---|---|
| import | 延迟导入重模块：`ui.pages.*` 在首次导航时导入；`matplotlib` 不使用 |
| 数据库 | 启动只 `PRAGMA` + 迁移检查，不预加载行情 |
| 首屏 | Dashboard 只查聚合数（`COUNT`），不等价于全表扫描 |
| 字体 | 启动时枚举一次字体，缓存结果 |
| 日志 | 控制台只 WARNING，文件异步（`QueueHandler` + `QueueListener` 可选；数据量小可同步） |

### 3.6 内存

- 1 万根 bar × 8 标的 ≈ 80k 对象 × ~200B ≈ 16MB（可接受）；
- 回测结果只保留权益曲线（1 万点 ≈ 0.5MB）与交易明细，不保留全部订单对象；
- 事件环形缓冲 500 条，超出覆盖；
- 页面切换不销毁（缓存），但页面内表格数据在 `on_hide()` 时清空大列表。

### 3.7 模拟盘与实盘实时性

- 模拟盘线程模型：1 个回放线程 + 主线程 UI；通过 `after(50)` 排空事件；
- tick 间隔 = `1.0 / speed` 秒，`speed ∈ {1,10,60,0(立即)}`；
- 立即模式下不 `sleep`，但每 200 根让出一次 `time.sleep(0)` 并检查停止标志；
- UI 更新合并：同一帧内多个 `live.tick` 只渲染最后一个（脏标记）。
- 实盘同步：`LiveTradeService._sync_loop()` 每 3 秒一次 `account/positions/orders` 查询，
  与 UI 完全解耦；回报走网关读线程 → `EventBus` → UI 队列，下单调用本身不等 UI。
- 实盘下单是「一次本地校验 + 一次网关调用」：风控、幂等、限额都在内存里完成，
  只有 `gateway.place_order()` 调 xtquant；延迟由本机 miniQMT 与券商柜台决定。
- 心跳：客户端每 3 秒 `ping`，10 秒无任何消息判离线；重连退避 1/2/4/8/15 秒，
  避免柜台繁忙时堆积请求。

## 4. 测量方法（实际交付版）

```bat
:: 回测基准：固定种子、内存库、默认 3 次，输出 P50/P95，超标退出码 1
python tools\bench_backtest.py --repeat 3 --memory --startup

:: 冷启动（容器装配，不含窗口）
python -X importtime -m tradesome --version
```

`tools/bench_backtest.py` 的口径：内置合成行情 1167 根/标的，跑
2022-01-04..2026-10-30 的 `ma_cross` 全程回测，P95 上限 2.0 秒。

**实测（2026-11-08，i5 级 CPU / Windows 10 / Python 3.9）**：

| 指标 | 实测 | 预算 | 结论 |
|---|---|---|---|
| 单次回测（1 标的、1167 根、含基准） | P50 0.484s / P95 0.506s | ≤ 2.0s | 通过，约 4 倍余量 |
| 回测峰值内存（tracemalloc） | 1.7 MB | ≤ 300MB | 通过 |
| 冷启动 `build_container`（内存库） | 0.022s | ≤ 3.0s | 通过 |
| 实盘 `start_session`（模拟柜台） | 0.010s | ≤ 1.0s | 通过，柜台握手另计 |
| 实盘 `place_order`（模拟柜台，含风控/入库） | 0.001s | ≤ 0.2s | 通过 |
| 实盘 `sync_now`（账户/持仓/委托） | < 0.001s | ≤ 0.5s | 通过，QMT 模式另加柜台 RTT |
| 全量测试（350 用例，含 UI 真实窗口） | 约 44–52s | — | 可接受 |

> 实盘延迟口径：本机模拟柜台、内存库、100 股限价单已成交；QMT 模式下 `sync_now`
> 与 `place_order` 的耗时主要由本机 miniQMT 到券商的往返决定，不在本软件内。
> 实测命令见 `python -c "..."`（见 `docs/13` §4.4 与本节脚本示例）。

> 说明：全量测试里的 4 个 UI 用例会真的开窗口，因此耗时有几秒抖动；其余用例
> 都在临时目录 + 内存库里跑，不读写 `var/`。

## 5. 已知瓶颈与取舍

| 瓶颈 | 现状 | 取舍 |
|---|---|---|
| Tk Canvas item 数量 | 250 根 K 线约 1500 item | 抽稀到 ≤ 250 根；不做无限缩放 |
| SQLite 单写者 | 导入时 UI 卡顿 | 导入放后台线程 + 进度条 |
| Python 循环 | 1 万 bar 约 0.6–1.2s | 可接受；不引入 C 扩展（离线约束） |
| 多标的全量读入 | 50 标的 × 3 年 ≈ 40MB | 限制单次回测 ≤ 20 标的 |
| 事件总线同步回调 | 订阅者慢会拖慢发布者 | 约定订阅者只做轻量入队；重活丢线程 |

## 6. 性能反模式（Review 必查）

1. 在 UI 线程里 `time.sleep` / `requests` / 大循环；
2. 在 `on_bar` 里 `SELECT` 数据库；
3. 每次重绘都新建 `PhotoImage` / `Font`；
4. 用 `str` 拼接万行文本（用 `"\n".join`）；
5. 对 `list` 做 `in` 判断（用 `set`）；
6. 每根 bar 都 `bus.publish`（节流到 1/50 或 100ms）；
7. 在 `Treeview` 里插入 1 万行（分页 200 行）；
8. 重复 `json.dumps` 大对象（缓存结果）。
