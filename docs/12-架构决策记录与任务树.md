# 第一部分：架构决策记录

## ADR-001 桌面技术栈选择 Tkinter

- **背景**：必须本地桌面、离线可运行；目标机器只有 Python 3.9 标准库，无法 `pip install`（实测 shell 内 DNS 不可用）；需要完全掌控视觉。
- **决策**：Tkinter（tk 8.6）+ ttk 主题 + Canvas 自绘图表。
- **备选**：
  - PySide6/PyQt5：视觉与控件更强，但无网络无法安装 → 排除；
  - Electron/Web：Node 存在但无 npm registry → 排除；
  - 浏览器 + 本地服务：不是"桌面端"，且需起端口 → 排除；
  - Dear PyGui/pygame：同样需安装 → 排除。
- **后果**：控件生态弱，需要自建按钮/卡片/表格样式；换来零安装、启动快、可完全定制。缺点是复杂动画能力有限，因此设计上避免重动画。

## ADR-002 零第三方依赖

- **背景**：目标环境离线；引入依赖意味着用户装不上。
- **决策**：仅标准库。`requirements.txt` 留空并说明。
- **备选**：numpy/pandas 加速（已预装但版本锁定 1.21/1.3）——核心计算量在 1 万 bar 量级，纯 Python 足够（实测约 1s），且避免版本差异。
- **后果**：指标与统计需自己实现（约 400 行），但语义可控、可测试、无 API 漂移。

## ADR-003 SQLite 作为唯一持久化

- **背景**：单机单用户，数据量 10 万–100 万行；需要事务、索引、崩溃恢复。
- **决策**：SQLite（WAL 模式），单文件 `var/tradesome.db`。
- **备选**：CSV/JSON 文件（无事务、易损坏）；DuckDB（需安装）；SQLAlchemy（已预装但引入 ORM 复杂度，且 1.4 API 与类型标注繁琐）。
- **后果**：需自己写迁移与仓储（约 500 行）；换来零依赖、可备份、可用任意 SQLite 工具查看。

## ADR-004 六边形架构 + 事件驱动

- **背景**：要求"所有模块可独立修改不影响其他模块"。
- **决策**：L1 core → L2 领域/适配器 → L3 app → L4 ui；跨模块通知走 `EventBus`；端口协议放 `ports.py`。
- **备选**：传统三层（UI→Service→DAO）——UI 容易直接依赖 DAO；MVC——桌面端控制器膨胀。
- **后果**：文件数与样板代码增加（每个适配器一个文件）；换来"换数据源只改一个文件"，并由 `test_architecture.py` 静态保障。

## ADR-005 回测采用"下一根 bar 开盘成交"

- **背景**：最常见、最致命的回测错误是用当日收盘价成交（等于用未来信息）。
- **决策**：T 日收盘后策略产生订单，T+1 日开盘撮合；市价单成交价 = 开盘价 ± 滑点；限价单需价格穿越才成交。
- **备选**：当日收盘成交（虚高）；当日 VWAP（仍含未来信息）；tick 级（数据不具备）。
- **后果**：回测收益低于"作弊版"，但更接近真实；文档与 UI 中明确提示"信号在收盘、成交在次日"。

## ADR-006 用户策略采用进程内 AST 沙箱

- **背景**：用户可能从网上复制策略代码，需防误用与明显恶意。
- **决策**：AST 白名单扫描（禁危险 import/调用/逃逸属性），同进程加载。
- **备选**：子进程 + 受限 token（Windows 上实现复杂、IPC 成本高、调试困难）；容器（不可用）；不限制（风险高）。
- **后果**：不是绝对安全（Python 同进程无法绝对隔离），定位为"护栏"；配合"无网络、无真实资金"降低影响面。若未来接入真实券商，升级为子进程隔离（记为待办）。

## ADR-007 密钥使用 Windows DPAPI

- **背景**：API Key 不能明文落盘；不能引入 `cryptography` 包。
- **决策**：`ctypes` 调 `CryptProtectData`（当前用户作用域）；非 Windows/失败时降级为 PBKDF2+XOR 并显式提示"弱保护"。
- **备选**：明文（不可接受）；自研 AES（无标准库实现，易错）；环境变量（仍需落盘）。
- **后果**：密文不可跨 Windows 用户/机器迁移，需在文档中说明。

## ADR-008 图表用 Canvas 自绘

- **背景**：matplotlib 已预装但风格与 UI 不统一、启动慢（~1.5s）、导出与交互受限。
- **决策**：`ui/charts.py` 自绘 K 线/折线/热力图/迷你线，统一设计令牌与抽稀策略。
- **备选**：matplotlib 嵌入（启动慢、主题难统一、Tk 后端交互弱）；pyqtgraph（需安装）。
- **后果**：需自己处理坐标、刻度、十字光标（约 700 行）；换来统一视觉、零依赖、可控性能。

## ADR-009 测试用 unittest 而非 pytest

- **背景**：pytest 未安装且无法安装。
- **决策**：`unittest` + `discover`；自建轻量夹具模块 `tests/support.py`。
- **后果**：参数化需手写循环；报告为文本；换来零依赖可执行。

## ADR-010 模拟盘用历史 bar 回放；实盘走独立网关（后被 ADR-014 扩展）

- **背景**：首版要求"实盘策略"，但本地软件不应也不能直接下真实单（合规 + 无券商接入 + 离线）。
- **决策**：实现完整订单生命周期与撮合，但券商适配器只有 `PaperBroker`；真实券商适配器仅留 `Broker` 协议与文档示例。
- **后果**：教学与验证价值完整。**2026-11-08 补充**：用户后续要求真实 A 股实盘，见 ADR-014；模拟盘仍保留为默认。

## ADR-011 单账户、单币种、人民币

- **背景**：个人用户场景；多账户会显著增加会计与 UI 复杂度。
- **决策**：一个 `Account` 实例、CNY、A 股规则。
- **后果**：不支持多策略分仓核算（未来可扩展 `sub_account` 字段）。

## ADR-012 配置用 JSON 文件而非数据库/环境变量

- **背景**：用户需要可读、可手改、可备份的配置。
- **决策**：`var/settings.json`，原子写，损坏自动备份恢复默认；环境变量仅覆盖少数路径项。
- **后果**：无 schema 版本化工具，用 `schema` 字段 + 容错读取解决。

## ADR-013 任务顺序：先写完所有代码再测试

- **背景**：用户明确要求"所有代码写完所有功能制作完毕后才能开始测试"。
- **决策**：P3–P11 只写代码与做语法级检查（`compileall`），P12 统一编写并执行测试，P13 集中修复。
- **后果**：缺陷发现滞后，P13 可能较长；换来符合用户对"完整性优先"的要求。风险控制：编码期严格遵守契约文档，减少返工。

## ADR-014 实盘采用"原生 QMT（xtquant）直连"，不依赖 vnpy

- **背景**：用户要求接入真实 A 股（参考 vnpy），随后进一步要求"直接原生接入，不依赖和安装 vnpy"。项目是 Python 3.9 + 零运行时依赖 + Tkinter，不能内嵌 vnpy（要求 3.10+），也不引入 vnpy。
- **备选**：A 内嵌 vnpy（版本与依赖冲突，否决）；B 自研柜台 C++ 封装（工作量与合规风险不可接受，否决）；C 独立 TCP 桥接进程调 vnpy（第一版做法，需用户安装 vnpy，已移除）；D 原生 `xtquant` 直连（选定）——`xtquant` 随券商 QMT/miniQMT 客户端分发，是纯 Python 包，不需要 pip 安装 vnpy。
- **决策**：TradeSome 定义自己的 `Gateway` 契约；`QmtGateway` 在进程内通过 `xtquant.xttrader` 连接本机已登录的 miniQMT，完成报单/撤单/账户/持仓/委托/成交查询与回报订阅。只保存 `userdata_mini` 目录、资金账号与账号类型，券商密码由 QMT 客户端保管。模拟柜台与 QMT 共用 `OrderRouter`、`RiskManager`、`OrderManager` 与同一套 UI。
- **后果**：本体零第三方依赖；真实使用需要券商 QMT 权限与已登录客户端；未安装/未登录/账号错误时给出中文提示；断线时在场单标 `UNKNOWN` 并对账，不猜成交。行情仍用本地日线 + 手工刷新，QMT 交易不依赖行情订阅。


## ADR-015 自由组合策略用条件 DSL，新手指引分三层

- **背景**：用户要求「不要让人只能在已有模板上改」「要有新手指引与操作教学」。若允许用户写脚本再执行，会破坏零依赖与沙箱边界；若只做模板，又无法从零组合。
- **备选**：A 生成 `.py` 再加载（引入代码执行面，否决）；B 只扩充模板数量（仍是改参数，不满足「新的策略方式」，否决）；C 声明式条件 DSL + 动态策略类（选定）；D 可视化节点图（实现与测试成本过高，暂不做）。
- **决策**：入场条件限定 6 种、退出 4 种，全部由 `strategy/rules.py` 解释；档案仍存 `strategy_profiles.spec_json`（新增 `kind`/`rules`，无需迁移）；引导采用「欢迎框 → 7 步跨页高亮 → 每页 3 步帮助」三层，状态只存 `kv onboarding.done`。
- **后果**：策略能力受 DSL 限制，但可校验、可摘要、可回测；新增条件只需改 `RULES_TYPES` 与 `RuleStrategy._match`，UI 自动生成字段。Tk 无透明窗口，引导不做全屏遮罩，改用边框+浮卡，避免遮挡页面。

## ADR-016 真实行情走 akshare 子进程，应用本体不依赖第三方库

- **背景**：用户要求「清空测试数据、全部使用真实数据、股票数据接入 akshare」。直接 `import akshare` 会把 pandas/requests 的版本冲突带进一个原本零依赖的桌面应用，也让打包体积翻几倍。
- **备选**：A 应用内直接 import akshare（打包与依赖风险大，否决）；B 把 akshare 的 HTTP 接口自己重写（要跟字段与反爬变化，维护成本高，否决）；C 独立工具进程抓取→写标准 CSV→复用现有导入链路（选定）；D 只支持手动下载 CSV（不满足"接入 akshare"）。
- **决策**：`tools/akshare_sync.py` 是唯一 import akshare 的地方；它只输出 CSV 与一行 JSON 摘要，`MarketService.sync_akshare()` 用子进程调用并解析，失败按标的隔离。CSV 清洗放在 `data/providers/akshare_csv.py`，不 import akshare，可单测。应用启动不再自动生成演示数据，`--demo` 仅保留给开发自检。
- **后果**：用户需自行 `pip install akshare` 并联网；软件本体仍可离线运行（CSV 导入）。换来的是依赖隔离、可替换数据源、可审计的中间 CSV；代价是多一个进程与一次落盘。

## P16 高 DPI 清晰度修复 ✅

- 问题：进程未声明 DPI 感知，Windows 在 125% 缩放下把整个窗口当位图拉伸，文字与细边框发虚；
  截图脚本只能靠乘 1.25 补偿坐标，治标不治本。
- 做法：
  - `tradesome/ui/__init__.py` 新增 `enable_dpi_awareness()`，在创建 Tk **之前**调用
    `SetProcessDpiAwarenessContext(-4)`，回退 `shcore.SetProcessDpiAwareness(2)`、`user32.SetProcessDPIAware()`；
  - `Shell` 读取 `winfo_fpixels("1i")/96` 写入 `theme.set_dpi()`，并显式设置 Tk `scaling = dpi/72`；
  - `theme.px()` 改为 `v × user_scale × dpi_factor`，页面/控件/图表全部经它取尺寸；字体仍用 pt，不重复乘；
  - `_ChartBase` 的 padding 与画布高度走 `theme.px()`；截图脚本去掉 1.25 补偿。
- 验收：125% 下文字与边框锐利；11 页截图 `errors: []` 且无裁切；295 个测试全绿；100% DPI 下布局不回退。
- 文档：docs/08 §7.1、docs/13 第 21 条缺陷、README FAQ、docs/00 版本表。

## P17 macOS 风格视觉重构 ✅
